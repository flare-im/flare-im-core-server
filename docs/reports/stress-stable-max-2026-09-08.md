# Flare IM 稳定最大承载压测报告

日期：2026-09-08　被测环境：生产 118.107.9.221（单机全栈 Docker）
被测版本：conversation v44 / orchestrator v43 / push-server v45 / message-ingest v46 / storage-reader v46；KV=Dragonfly df-v1.40.2（8 线程）
测试目标：在**保持稳定**的前提下，实测单机能承载的最大「真实认证在线 + 大群 + 消息吞吐」，为后续项目部署提供配置参考。

## 执行摘要

单机 8核/15.6G 在 **2.5 万真实认证在线 + 5 个 10 万人群 + 313 msg/s 广播投递**下稳定运行 30 分钟：累计 **56.5 万条消息、成功率 99.998%、持久化零错误、PG 零卡死、连接零掉线**，内存留 4.3G 余量。真在线**安全边缘 ~2.8 万**；32k 能建立但内存降到安全线边缘（2.7G），非稳定工作点，稳定持 32k+ 需 24G+ 内存。所有连接均为**真 token 认证 + 真 WS 会话 + 心跳保活**（非裸连接刷量）。

## 二、稳定最大承载（30 分钟实测）

**方法**：用 web app 同款 SDK 托管流程为 25,000 个用户签发有效 token，经 flare-core 客户端建立 **25,000 个真实认证 WebSocket 长连接**（每连接带 token + device_id + 心跳，网关认证持有）；同时对 **5 个 10 万人群**并发高强度发送消息（24 线程 × 100 条/批），每条群消息向该群 25,000 个在线成员做**真实广播扇出**。全程内存安全闸守护。

| 能力项 | 实测值 |
|---|---|
| 真实认证在线 | **25,000**（WS 会话全程保持，掉线 0） |
| 并发大群 | **5 × 10 万人群** |
| 运行时长 | **1,803 s（30 min）跑满** |
| 累计发送 | **565,691 条**（失败 9，成功率 99.998%） |
| 平均吞吐 | **313 msg/s**（含对 2.5 万在线的真实广播投递） |
| 批延迟（100 条/批） | P50 7.5s / P95 10.7s / P99 12.0s（24 并发批下的排队延迟；单条摊薄 ~75ms） |
| 持久化错误 | **0 / 565,691**（storage-writer 全程零错误） |
| PG 慢查询(>2s) | **全程 0~1**（无卡死，对比历史 101% 单核卡死已根治） |
| 安全闸 | **未触发**（内存全程安全） |

## 三、承载上限与安全边界

| 维度 | 稳定推荐 | 硬上限 | 说明 |
|---|---|---|---|
| 真实认证在线 | **2.5 万** | ~2.8 万 | 硬上限受①临时端口(~28k/源IP)②网关内存(~130KB/连接) 双限制；2.8 万是崩溃边缘，稳定应取 2.5 万留余量 |
| 消息吞吐(群广播) | **~313 msg/s** | ~400 msg/s | 400 是无接收端的服务端上限；有 2.5万在线真实扇出时约 313；瓶颈在发送主链(seq+持久化)非 KV |
| 单聊吞吐 | **~1,200 msg/s** | — | 单聊无大群扇出，吞吐远高于群 |
| 并发 10 万群 | **5 个（本测）** | 更多需实测 | 大群扇出已与群规模解耦(orchestrator 会话级读扩散)，PG 无 O(成员) 扫描 |

**32k 专项实测（多目标 IP 绕端口限）**：loadconns 改轮转 6 个目标 IP（127.0.0.1-6:60051，各独立 ~28k 端口空间）后，**32,000 连接全部建立、0 失败**——证明端口限可绕过。但**持有 32k 时系统可用内存降到 2,739MB**，触发内存安全闸（<2,800MB）自动杀连接、机器未 thrash。结论：**32k 能建立但内存余量仅 ~2.7G（安全线边缘），非稳定工作点**；稳定持有 32k+ 需 24G+ 内存机。安全闸机制经此验证有效（对比早前 6 万无防护压垮机器）。

## 四、可靠性验证（高压下的正确性保障）

压测不仅看吞吐，更验证正确性铁律在高压下不破：

| 保障项 | 验证结果 |
|---|---|
| **消息持久化** | 56.5 万条 storage-writer **零错误**，deliver-then-persist 链路全程可靠 |
| **seq 一致性** | 全程 seq ≥ events_max、无回退撞号（历史 KV 清空致撞号事故已根治） |
| **seq floor 自愈（v46）** | head 查询由 `ORDER BY seq DESC`→`created_at DESC`（压缩表 orderby 列，走 chunk 元数据）+ floor 超时 800→2000ms；30min 压测 **floor 降级/超时 0 次**，head 查询 272ms（<2s）。仅对突发大量插入后的陈旧统计短暂敏感，autovacuum 自修复且首触降级 plain INCR 对温热 key 无害 |
| **发送成功率** | 99.998%；9 例失败经查为**客户端 grpcurl 高压瞬时噪声**（服务端/持久化零错误），非服务缺陷 |
| **PG 稳定性** | 多核 231-327%、慢查询全程 0~1，历史「101% 单核卡死 39min」已根治（阶段1 未读有界探测 + push 大群短路 + ANALYZE） |
| **内存安全闸** | 可用内存 <2.8G 自动杀连接持有方；32k 测试中正确触发、机器未崩溃 |

> 发送失败的另一类（非本测）：单聊要求发送方是会话成员，非成员发送方被网关正常拒绝（预期行为，非缺陷）。群测用真实成员账号无此问题。

## 五、消息吞吐分解

| 场景 | 吞吐 | 瓶颈 |
|---|---|---|
| 单聊 | ~1,200 msg/s | 发送主链(seq 分配 + 持久化)，无扇出 |
| 群消息（无在线接收端） | ~400 msg/s | 服务端发送主链饱和（8→48 线程吞吐不变） |
| 群消息（2.5 万在线真广播） | ~313 msg/s | 叠加对在线成员的实时广播扇出投递 |

关键：吞吐瓶颈在**发送主链（seq + 持久化）**，不在 KV（Dragonfly 8 线程未饱和）；大群扇出已与群规模解耦，5 群与 1 群的单条成本一致。

## 六、部署配置参考（按目标规模选型）

以本机实测为基线线性外推（架构已解耦，连接与吞吐随内存/核数近似线性）：

| 目标规模 | 建议配置 | 依据 |
|---|---|---|
| ~2.5 万在线 / 5 大群 / 300 msg/s | **单机 8核 / 16G**（本机） | 实测稳定，留 4G 余量 |
| ~5 万在线 / 10 大群 / 600 msg/s | 单机 16核 / 32G | 网关 ~7G + PG/KV 扩容；或 2 台本机规格 |
| ~10 万在线 / 1000+ msg/s | 2~3 台 16核/32G（网关水平扩展）+ 独立 PG/Dragonfly | 网关按连接数水平扩，PG/KV 垂直+读写分离 |
| 100 万在线 | 网关集群(10+ 节点) + Dragonfly 集群 + PG 分片/只读副本 | 单机结论不外推；需专项容量设计 |

**关键选型原则**：
- **网关内存 = 在线数 × 130KB + 基线 ~0.5G**（连接是网关的主内存消耗）。
- **PG 是持久化瓶颈**（非 KV）；shared_buffers 取 mem×0.25、effective_cache_size 取 mem×0.6；events 表已 TimescaleDB 压缩（95% 比）。
- **Dragonfly 8 线程吃满多核**，已消除单线程 Redis 中枢瓶颈，KV 通常不是瓶颈。
- **物理内存铁律**：∑容器 mem_limit ≤ 物理×0.92；每容器都设限；进程内配额 < 容器上限。

## 八、事故与教训（已固化）

直接冲 **6 万连接**曾把本机压入 swap thrash、SSH/HTTP 约 30 分钟无响应（后自愈未重启）。6 万连接需 ~8.6G 网关内存，单机 15.6G 不可行。**大连接压测铁律**：
1. 先算内存预算（在线数 × 130KB + 客户端 + 服务）≤ 物理 × 安全系数，分档爬升（5k→25k 看内存曲线）预判上限。
2. **内存安全闸必挂**（可用内存低于阈值自动杀连接持有方）。
3. gentle 建连并发（CONNECT_CONC 别过高，避免客户端瞬时任务风暴）。
