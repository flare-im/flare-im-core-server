# Flare Capability

English · [中文](README.zh-CN.md)

Flare IM **capability service**: the **Hook engine** (configuration and gRPC dispatch) + the **capability extension subsystem** (DDD: the `domain/capability` domain model and ports; CQRS: `application` contains only **`commands` / `handler` / `queries`**; infrastructure: under `infrastructure/capability`, split into **`registration` / `dispatch` / `routing`** packages). The process assembly entry point is **`composition`** (`process_config` / `runtime_context` / **`wiring`** / `bootstrap` / `hook_registry`; formerly `service`).

## Core responsibilities

- **Configuration management**: supports three configuration sources — configuration file, dynamic API (database), and configuration center.
- **Execution dispatch**: executes hooks by priority, with support for concurrent execution and timeout control.
- **Execution evidence and circuit breakers**: records hook executions in `hook_executions` (failures in full, successes sampled), serves their statistics, and breaks the circuit per (tenant, hook); see [Execution evidence and circuit breakers](#execution-evidence-and-circuit-breakers).
- **Extension mechanism**: supports three extension methods — gRPC, WebHook, and Local Plugin (on the hook transport side); the hook's gRPC surface (`HookExtension` / `HookService`) shares the same file **`capability_service.proto`** and the same package **`flare.capability.v1`** with `CapabilityService`, and on the Rust side is unified under `flare_grpc_proto::capability`.
- **Capability extension**: aggregates Guard / Resolver via `CapabilityExtensionRegistry`; plugins are managed (authorized by the tenant's plugin projection) and register their endpoints with `RegisterPluginEndpoint`. Core knows no concrete plugin: calls, polls and the like are plugins built on business-neutral host capabilities. The capability catalog, authorization, and command dispatch are exposed via **`flare.capability.v1.CapabilityService` gRPC** on the same server as this process's hook port; external HTTP is forwarded to this gRPC by the access gateway (there is no legacy plugin host or outbox).

### Capability gRPC (`CapabilityService`)

Consistent with `port` in `config/base.toml` (default **50051**); the client uses the `CapabilityServiceClient` generated by `flare-grpc-proto`. Main RPCs: `ListCapabilities`, `ListUserCapabilities`, `Dispatch`, `GrantUserCapability`, `RevokeUserCapability`, `SetTenantCapabilitySwitch`. The `payload_json` of `Dispatch` is a JSON string, for example for `example.poll.vote`:

```json
{ "codec": "VP8" }
```

When the process is configured with **`database_url`**, the authorization / tenant switches of `CapabilityService` go through **`PostgresCapabilityPolicy`**, sharing a connection pool with the hook configuration; both the hook and capability tables live in the "Hook engine + Capability policy" section of **`deploy/init.sql`** (`hook_configs`, `hook_executions`, `capability_user_grants`, `capability_tenant_switches`, `capability_service_settings`, `capability_audit_log`, etc.; that section performs **`DROP TABLE IF EXISTS ... CASCADE` followed by `CREATE TABLE`** for all the aforementioned objects). If you get the error `relation "capability_service_settings" does not exist`, it means the table does not exist in the **PostgreSQL instance that flare-capability is currently connected to**: a common cause is that **the script ran against a different instance/database** (for example, the orchestrator uses `5432`, while the standalone process **`flare-capability` connects to `DATABASE_URL`, or else to the postgres profile of `[services.capability].postgres` (`[postgres.media]` when unset) in the loaded configuration; with neither it refuses to start** instead of falling back to a built-in connection string, see `composition/bootstrap.rs`). At startup a `flare_capability::db` log is printed (the redacted `host:port/dbname`); please align it with the target where `deploy/init.sql` is executed. **Note**: that section drops and recreates the Hook/Capability-related tables; for a production database, evaluate the data using a migration process. When no database is configured, **`InMemoryCapabilityGrants`** is used and development sample grants are injected.

**`user capability grant missing or expired`**: `Dispatch` could not find a non-expired row in `capability_user_grants` matching **tenant_id + user_id + capability_id** (including `namespace.*`). The orchestrator defaults to **tenant_id = `0`** (see `ctx.tenant_id().unwrap_or("0")`). `user_id = *` means any user under that tenant (development-friendly; in production, populate per user). For example:

`INSERT INTO public.capability_user_grants (tenant_id, user_id, capability_id, plan_code, source) VALUES ('0', '*', 'example.*', 'dev', 'manual') ON CONFLICT DO NOTHING;`

### Plugin registrations (`RegisterPluginEndpoint`)

A plugin endpoint reaches the route book by **registration**: `CapabilityService.RegisterPluginEndpoint` / `DeregisterPluginEndpoint`, called by platform staff through Admin Gateway (`core:plugins:write`) or by a plugin host with a Cell-signed `Service` context for its own tenant. With a database, Capability writes the registration to `capability_plugin_endpoints` (migration `0011`) first and only then adds it to its in-memory route book; a failed write fails the call with `UNAVAILABLE` and changes nothing. A deregistration deletes the row first.

Every Capability instance loads the table at startup (a missing table stops startup: run the migrations), re-reads it periodically so the instances converge, and survives a restart without losing registrations. A local write newer than a refresh snapshot is not overwritten by that snapshot. Healthy registrations get `last_healthy_at` after each health round; a registration that was neither re-registered nor healthy within the TTL is deleted (checked once a minute) and disappears from the other instances on their next refresh. Without a database, registrations are process-local: other instances do not see them and a restart loses them (the startup log says so once).

| Setting (environment variable, then `[capability_runtime]` key) | Default | Allowed |
| --- | --- | --- |
| `FLARE_CAPABILITY_PLUGIN_ROUTE_REFRESH_SECS` / `plugin_route_refresh_secs` | 10 | 1 to 3600 seconds |
| `FLARE_CAPABILITY_PLUGIN_ROUTE_TTL_SECS` / `plugin_route_ttl_secs` | 86400 | 300 seconds to 30 days |

A value outside the range is ignored and the default applies.

### `ExtensionPlugin` identity

The `ExtensionPlugin` router (`flare.capability.v1.ExtensionPlugin/Call`) sits behind the signed-context layer with anonymous admission. The verified `x-flare-ctx` is the only identity: `GenericRequest.metadata`, `x-tenant-id`, `x-user-id` and similar caller metadata are never read.

- `flare.capability.v1.health_check` is the only operation answered without a context; an invalid context is refused with `UNAUTHENTICATED` even there.
- Every other operation needs a signed `User`, `Service` or `TenantAdmin` context: without one it is `UNAUTHENTICATED`. `Staff`, `System` and `Guest` contexts, and a tenant that is empty, `*` or padded with blanks, are `PERMISSION_DENIED`. Staff reach Core only through Admin Gateway.
- The handler receives the verified context, so tenant, user, actor, request id and trace id come from the signature. `flare.media.v1.list_plugin_routes` lists the signed tenant's plugins only; a `tenant_id` in its body must be empty or that tenant.
- Without a Cell key set (`FLARE_INTERNAL_CTX_PUBLIC_KEYS` / `FLARE_INTERNAL_CTX_PUBLIC_KEY`) the router is served without the layer and answers only the health check; every other call is `UNAUTHENTICATED`.

## Hook configuration sources

In this service, hook configuration supports three sources, ordered from highest to lowest priority:

### 1. Dynamic API configuration (highest priority)

**Storage location**: PostgreSQL database

**Characteristics**:
- Supports multi-tenant isolation
- Supports dynamic create/read/update/delete
- Supports version management
- Supports audit logging (records creator, creation time, update time)

**Table structure**: refer to **`deploy/init.sql`** as the source of truth (which includes columns such as `group_name`, `require_success`, `metadata`, and `created_by` aligned with `PostgresHookConfigRepository`). The following is a conceptual illustration:

```sql
CREATE TABLE hook_configs (
    id BIGSERIAL PRIMARY KEY,
    tenant_id TEXT,                    -- Tenant ID (optional, for multi-tenant isolation)
    hook_type TEXT NOT NULL,            -- Hook type (pre_send, post_send, etc.)
    name TEXT NOT NULL,                 -- Hook name
    version TEXT,                       -- Hook version
    description TEXT,                   -- Hook description
    enabled BOOLEAN NOT NULL DEFAULT true,
    priority INTEGER NOT NULL DEFAULT 100,
    group_name TEXT,                    -- Hook group (validation/critical/business)
    timeout_ms BIGINT NOT NULL DEFAULT 1000,
    max_retries INTEGER NOT NULL DEFAULT 0,
    error_policy TEXT NOT NULL DEFAULT 'fail_fast',
    require_success BOOLEAN NOT NULL DEFAULT true,
    selector_config JSONB NOT NULL DEFAULT '{}',  -- Selector configuration
    transport_config JSONB NOT NULL,               -- Transport configuration
    metadata JSONB,                                -- Metadata
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by TEXT,                               -- Creator
    
    UNIQUE(tenant_id, hook_type, name)  -- Unique constraint
);
```

**Usage** (start the full process, including the gRPC and optional plugin surface):
```rust
use anyhow::Result;
use flare_capability::domain::model::ExecutionMode;
use flare_capability::composition::{ApplicationBootstrap, CapabilityServiceConfig};

#[tokio::main]
async fn main() -> Result<()> {
    let config = CapabilityServiceConfig {
        database_url: Some("postgresql://user:pass@localhost:5432/flare".to_string()),
        tenant_id: Some("tenant-a".to_string()),
        config_file: Some("config/hooks.toml".into()),
        config_center_endpoint: Some("etcd://localhost:2379".to_string()),
        execution_mode: ExecutionMode::Sequential,
        ..Default::default()
    };
    ApplicationBootstrap::run(config).await
}
```

**Configuration management API** (via PostgresHookConfigRepository):
```rust
// Save hook configuration
repository.save(
    Some("tenant-a"),
    "pre_send",
    &hook_config_item,
    Some("admin")
).await?;

// Delete hook configuration
repository.delete(
    Some("tenant-a"),
    "pre_send",
    "hook-name"
).await?;
```

### 2. Configuration center (medium priority)

**Storage location**: etcd or Consul

**Characteristics**:
- Supports multi-tenant isolation
- Supports configuration-change watching (watch)
- Suitable for distributed environments

**Configuration key format**:
- Multi-tenant: `/flare/hooks/{tenant_id}/config`
- Global: `/flare/hooks/config`

**Usage**:
```rust
use flare_capability::domain::model::ExecutionMode;
use flare_capability::composition::CapabilityServiceConfig;

let config = CapabilityServiceConfig {
    config_center_endpoint: Some("etcd://localhost:2379".to_string()),
    tenant_id: Some("tenant-a".to_string()),
    execution_mode: ExecutionMode::Sequential,
    ..Default::default()
};
```

**Configuration format** (JSON):
```json
{
  "pre_send": [
    {
      "name": "friendship-check",
      "priority": 5,
      "timeout_ms": 50,
      "enabled": true,
      "require_success": true,
      "selector": {
        "tenants": ["tenant-a"],
        "conversation_types": ["single"]
      },
      "transport": {
        "type": "grpc",
        "endpoint": "https://hooks.relation.svc:7443"
      }
    }
  ]
}
```

### 3. Configuration file (lowest priority)

**Storage location**: local TOML file

**Characteristics**:
- Suitable for development environments and for platform-wide hooks that apply to every tenant
- Re-read at every refresh (see "Configuration refresh")

**Configuration file path**: `CONFIG_FILE`, default `config/hooks.toml` (relative to the working directory)

**Loading rules**:
- The file is optional. Without it Capability runs with no file hooks, and the startup log says so at INFO; otherwise it logs the path and the hook count.
- A file that exists but cannot be used stops Capability at startup: it cannot be read (permissions, a directory, not UTF-8, a symbolic link to a missing file), it is not a hook configuration (a TOML syntax or field type error, or a top-level table that is not one of the 15 hook types, such as `[[pre_sned]]`), or a hook in it fails validation (priority, timeout, group, error policy, empty webhook secret, reserved webhook header). The file is checked before the configuration center and the database, so a database outage cannot hide the error.
- The error names the file, the line and column of a parse error, and the hook and header names of a validation error. It never repeats the file's content: the TOML parser's own message quotes the offending line (and a field type error its value), which may hold a webhook secret or an authorization header.
- A file that becomes unusable while Capability runs does not stop the service: the file's hooks stay at the last version that loaded, every refresh logs the error at ERROR, and the other sources keep refreshing. The next refresh after the file is fixed loads it. Deleting the file removes its hooks at the next refresh.
- Unknown keys inside a hook entry are ignored by Capability (Message Ingest, which may read the same file, rejects them).

**Configuration example**:
```toml
[[pre_send]]
name = "friendship-check"
priority = 5
timeout_ms = 50
enabled = true
require_success = true

[pre_send.selector]
tenants = ["tenant-a"]
conversation_types = ["single"]
message_types = ["text", "image"]

[pre_send.transport]
type = "grpc"
endpoint = "https://hooks.relation.svc:7443"

[pre_send.retry]
max_retries = 3
retry_interval_ms = 100
backoff_strategy = "exponential"
```

## Configuration priority and merge rules

1. **Priority order**: database configuration > configuration-center configuration > configuration-file configuration
2. **Merge rule**: for hooks with the same name, the higher-priority configuration overrides the lower-priority one
3. **Load order**: loaded from lowest to highest priority, so the last-loaded configuration overrides earlier same-name configurations

## Multi-tenant support

Hook configuration supports multi-tenant scenarios:

- **Tenant isolation**: each tenant can have its own independent hook configuration
- **Global configuration**: a configuration with `tenant_id` = `NULL` (and the configuration file) applies to all tenants
- **Tenant configuration**: a tenant's own hooks run for that tenant only, in addition to the global ones; they cannot replace a global hook. The name of a global hook is reserved within its hook type: Administer rejects a tenant create/update that uses it with `ALREADY_EXISTS` (a disabled global row reserves its name too), and a same-named tenant row written some other way is not loaded (a warning is logged) while the global hook keeps running
- **Selector**: a non-empty `selector.tenants` limits a hook to the listed tenants

**Loading and execution** (process without `TENANT_ID`, the multi-tenant default):
the database loader keeps global rows as the global configuration and puts each
tenant's rows (registered through `CapabilityService/Administer`) into a bucket of
that tenant. `HookPlugin.Call` selects the hooks by the tenant of the caller's
signed context: global hooks plus that tenant's bucket. A tenant's invalid rows only
keep that tenant on its previous hooks; a failed source keeps its last loaded hooks.
An Administer write reloads that tenant's bucket immediately on the instance that
handles it, and announces the change with a PostgreSQL `NOTIFY` on
`flare_hook_config_changed`: every other instance sharing the database reloads the same
tenant (everything, for a global row) without waiting for the periodic refresh. A
listener that reconnects reloads everything once to cover notifications it missed; the
periodic refresh remains the fallback. The listener uses a PostgreSQL connection of its
own, outside the repository pool (one more connection per instance), and stops with the
process. Each tenant reload logs the tenant and its hook
count at INFO. A process started with
`TENANT_ID` keeps the single-tenant behaviour (no name reservation) and loads, as
global configuration:
```sql
SELECT * FROM hook_configs
WHERE enabled = true
  AND (tenant_id IS NULL OR tenant_id = 'tenant-a')
ORDER BY hook_type, priority ASC
```

**Callers**: `HookPlugin.Call` accepts only Cell-signed contexts (`x-flare-ctx`,
verified with `FLARE_INTERNAL_CTX_PUBLIC_KEY`). Unsigned or unverifiable calls get
`UNAUTHENTICATED`; a request body whose tenant or user disagrees with the signature
gets `PERMISSION_DENIED`. Without the public key every call is rejected.

## Configuration refresh

Hook configuration hot-refresh is supported:

- **Refresh interval**: 60 seconds by default (configurable via `refresh_interval_secs`)
- **Auto-refresh**: periodically reloads configuration from all configuration sources
- **Failures**: a source that fails to load keeps its last loaded hooks and the refresh logs the failure (ERROR for the configuration file, WARN for the database and the configuration center); an invalid merged global configuration leaves the current hooks unchanged. A refresh never stops a running service.
- **Startup**: of the three sources only the configuration file must load (see "Configuration file"). Loading the hook rows from the database or the configuration center may fail at startup; the failure is logged and the next refresh retries. The database connection itself is still required.

## Usage examples

### Basic usage

```rust
use anyhow::Result;
use flare_capability::domain::model::ExecutionMode;
use flare_capability::composition::{ApplicationBootstrap, CapabilityServiceConfig};

#[tokio::main]
async fn main() -> Result<()> {
    let config = CapabilityServiceConfig {
        config_file: Some("config/hooks.toml".into()),
        // No built-in fallback: the database is configured explicitly.
        database_url: Some(std::env::var("DATABASE_URL").expect("set DATABASE_URL")),
        config_center_endpoint: Some("etcd://localhost:22379".to_string()),
        tenant_id: Some("tenant-a".to_string()),
        execution_mode: ExecutionMode::Sequential,
        refresh_interval_secs: 60,
        ..Default::default()
    };
    ApplicationBootstrap::run(config).await
}
```

To execute hooks such as PreSend within a business process, use `flare_im_hooks::HookDispatcher` (in the same process as the orchestrator); this binary is mainly responsible for the hook-extension gRPC and the capability-plugin runtime.

```rust
use flare_capability::infrastructure::persistence::PostgresHookConfigRepository;

// Create a configuration repository

```

```

│   ├── models.rs        # Hook configuration models, execution plans
│   ├── repositories.rs  # Repository interfaces

│   └── service.rs       # Application service facade

```

## Configuration item reference

### Hook configuration item (HookConfigItem)

| Field | Type | Description | Default |
|------|------|------|--------|
| `name` | String | Hook name (required) | - |
| `priority` | i32 | Priority (0-1000; the smaller, the higher) | 100 |
| `group` | String | Group: `validation`, `critical` or `business` (case-insensitive); other values are rejected. Without it, priority >= 100 is `validation`, else `business`. A `critical` hook that is unreachable or times out always rejects; `business` hooks never stop the chain | by priority |
| `timeout_ms` | u64 | Timeout (milliseconds) | 1000 |
| `enabled` | bool | Whether enabled | true |
| `require_success` | bool | Whether success is required | true |
| `error_policy` | String | Error policy (fail_fast/retry/ignore) | fail_fast |
| `max_retries` | u32 | Maximum number of retries | 0 |
| `selector` | HookSelectorConfig | Selector configuration | - |
| `transport` | HookTransportConfig | Transport configuration | - |

### Hook selector (HookSelectorConfig)

Used to match hook execution conditions:

| Field | Type | Description |
|------|------|------|
| `tenants` | Vec<String> | Tenant list (empty means match all tenants) |
| `conversation_types` | Vec<String> | Conversation-type list (empty means match all types) |
| `message_types` | Vec<String> | Message-type list (empty means match all types) |
| `user_ids` | Vec<String> | User-ID list (empty means match all users) |
| `tags` | HashMap<String, String> | Tag matching |

### Hook transport configuration (HookTransportConfig)

Supports three transport methods:

1. **gRPC transport**:
   ```toml
   [transport]
   type = "grpc"
   endpoint = "https://hooks.example.com:7443"
   ```

2. **WebHook transport**:
   ```toml
   [transport]
   type = "webhook"
   endpoint = "https://hooks.example.com/webhook"
   secret = "your-secret-key"
   ```
   With a secret, deliveries carry `Flare-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, t "." raw-body)>`,
   the same contract as Core's webhook adapter (`docs/HOOK-PLUGIN-CONTRACT.md` §7); the
   old `X-Hook-Signature` is gone. The secret is write-only: `hook_config.create`, `get`,
   `list` and `update` never return it (`transport.metadata["signing_secret_configured"]`
   says whether one is set), an `update` with an empty secret keeps the stored one, and
   neither logs nor audit records carry it; an `update` with an empty secret and
   `transport.metadata["clear_signing_secret"] = "true"` removes it (unsigned delivery).
   Header values, like gRPC `metadata` values, are read back only as their keys with the
   value `<redacted>`; on `update` an empty or `<redacted>` value keeps the stored one.
   `secret = ""` in the file or config center is rejected at load; omit `secret` to send
   unsigned. A context without a tenant is not delivered.
   The gRPC transport forwards the caller's signed context (`x-flare-ctx`) and does not
   call without one.

3. **Local Plugin transport**:
   ```toml
   [transport]
   type = "local"
   target = "plugin-name"
   ```

## Execution evidence and circuit breakers

Every hook that `HookPlugin` calls for `pre_send`, `post_send`, `delivery` and `recall` goes
through a circuit breaker per (tenant, hook) and leaves an execution record in
`hook_executions` (source DDL `0015_20261016_hook_execution_evidence.sql`).

- **Circuit breaker**: keyed by the signed tenant, the hook type and the hook name, and kept per
  Capability instance. `failure_threshold` consecutive failures or timeouts, each within
  `failure_window_secs` of the first one, open it for `open_secs`; while it is open the hook is
  not called. A required hook (critical group, or `require_success`) then behaves like an
  unavailable hook: PreSend and Recall answer a retryable `UNAVAILABLE` (Message Ingest returns
  503), PostSend and Delivery fail with `UNAVAILABLE`; an optional hook is skipped. When the
  window ends one call probes the hook: success closes the breaker, failure opens it for another
  window, and other calls are short-circuited while the probe is outstanding. An answer, allow or
  reject, counts as healthy. Openings, failed probes (the 1st, 2nd, 4th, 8th, ...) and closings
  are logged with the tenant and hook name escaped; single short circuits only at DEBUG.
- **Records**: tenant, hook type and name (`hook_id` is `hook_type:name`), hook version, message
  id, request and trace ids, whether the hook answered (`success`), latency, error code, a fixed
  message, time and `sample_weight`. Never the message body or the downstream error text: a
  failure stores its error code and "hook call failed", a rejection `HOOK_REJECTED` and the
  hook's reason code, a timeout `HOOK_TIMEOUT`, a short circuit `HOOK_CIRCUIT_OPEN`. Rejections,
  failures and timeouts are kept in full. Allowed calls and short circuits are kept 1 in N, N
  being `1 / success_sample_ratio` rounded (0.01 keeps 1 in 100, 0.3 keeps 1 in 3), and the kept
  row has `sample_weight` N.
- **Write path**: the message path only adds the record to a bounded in-memory buffer (one lock,
  no waiting). A background task writes a batch as soon as `batch_size` records wait and every
  `flush_interval_ms`; at shutdown it writes what is left within 5 seconds, each batch's write
  cut off at that limit, and then closes the buffer: the records still left, a batch cut off and
  records handed in afterwards by requests still finishing are counted as `shutdown` drops. When
  the buffer is full a sampled record goes first: an incoming one is dropped, and an incoming
  full-kept record replaces the oldest buffered sampled one; a buffer holding only full-kept
  records drops the incoming record. A batch whose write fails or takes longer than 10 seconds is
  dropped, not retried. Every drop is counted.
- **Retention**: every `retention_sweep_secs` a task deletes rows older than `retention_days`,
  oldest first, at most `retention_delete_batch` rows per statement.
- **Reading**: `hook_config.get_statistics` and `hook_config.query_executions` (`Administer`)
  read only the rows of the caller's tenant for that hook. Counts are weighted estimates; average
  and p99 latency are weighted and leave short circuits out; `circuit_break_count` counts short
  circuits and `error_count_by_code` counts failures by code (a rejection is a success, not an
  error). Statistics cover the last 24 hours unless a range is given; executions come newest
  first, up to `limit` (at most 1000) with `has_more`.
- Without a database the breakers still run and nothing is recorded.

| Setting (environment variable, then key) | Default | Allowed |
| --- | --- | --- |
| `FLARE_CAPABILITY_HOOK_EXECUTIONS_ENABLED` / `hook_executions.enabled` | true | true or false |

| `FLARE_CAPABILITY_HOOK_EXECUTIONS_BATCH_SIZE` / `hook_executions.batch_size` | 500 | 1 to 5000, at most the capacity |

| `FLARE_CAPABILITY_HOOK_CIRCUIT_ENABLED` / `hook_circuit.enabled` | true | true or false |
| `FLARE_CAPABILITY_HOOK_CIRCUIT_FAILURE_THRESHOLD` / `hook_circuit.failure_threshold` | 5 | 1 to 1000 |
| `FLARE_CAPABILITY_HOOK_CIRCUIT_FAILURE_WINDOW_SECS` / `hook_circuit.failure_window_secs` | 30 | 1 to 3600 seconds |
| `FLARE_CAPABILITY_HOOK_CIRCUIT_OPEN_SECS` / `hook_circuit.open_secs` | 20 | 1 to 3600 seconds |

The keys are read from the runtime configuration file (`config/services/capability.toml`); a
value out of range is ignored and the default applies.

Metrics (hook names are never labels): `capability_hook_execution_records_queued_total`,
`capability_hook_execution_records_written_total`,
`capability_hook_execution_records_dropped_total{reason=buffer_full|write_failed|shutdown, class=sampled|always}`,
`capability_hook_execution_records_buffered`, `capability_hook_execution_flushes_total{result}`,
`capability_hook_execution_records_expired_total`,
`capability_hook_circuit_transitions_total{tenant_id, transition=opened|reopened|closed}`,
`capability_hook_circuit_short_circuits_total{tenant_id}` and `capability_hook_circuits_open`,
next to the generic gRPC server metrics (`GrpcMetricsLayer`).
