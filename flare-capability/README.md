# Flare Capability

English · [中文](README.zh-CN.md)

Flare IM **capability service**: the **Hook engine** (configuration and gRPC dispatch) + the **capability extension subsystem** (DDD: the `domain/capability` domain model, ports, and the **Dispatch domain service**; CQRS: `application` contains only **`commands` / `handler` / `queries`**; infrastructure: under `infrastructure/capability`, split into **`registration` / `dispatch` / `routing` / `internal`** packages, where RTC is currently wired via a remote media-control gRPC adapter and auto-registration). The process assembly entry point is **`composition`** (`process_config` / `runtime_context` / **`wiring`** / `bootstrap` / `hook_registry`; formerly `service`).

## Core responsibilities

- **Configuration management**: supports three configuration sources — configuration file, dynamic API (database), and configuration center.
- **Execution dispatch**: executes hooks by priority, with support for concurrent execution and timeout control.
- **Monitoring and statistics**: collects hook execution metrics and provides monitoring and alerting capabilities.
- **Extension mechanism**: supports three extension methods — gRPC, WebHook, and Local Plugin (on the hook transport side); the hook's gRPC surface (`HookExtension` / `HookService`) shares the same file **`capability_service.proto`** and the same package **`flare.capability.v1`** with `CapabilityService`, and on the Rust side is unified under `flare_grpc_proto::capability`.
- **Capability extension**: aggregates Guard / Resolver / `RtcCapability` via `CapabilityExtensionRegistry`; the RTC backend is wired via `capability_runtime.plugin_discovery_endpoints` (`capability_id = rtc.media.control`) or the environment variable `FLARE_MEDIA_CONTROL_GRPC_ENDPOINT`. The capability catalog, authorization, and command dispatch are exposed via **`flare.capability.v1.CapabilityService` gRPC** on the same server as this process's hook port; external HTTP is forwarded to this gRPC by the access gateway (there is no legacy plugin host or outbox).

### Environment variables (capability extension)

| Variable | Description |
|------|------|
| `FLARE_MEDIA_CONTROL_GRPC_ENDPOINT` | Overrides the media-control gRPC address (when not set, it falls back to auto-discovery via `capability_runtime.plugin_discovery_endpoints`) |

### Capability gRPC (`CapabilityService`)

Consistent with `port` in `config/base.toml` (default **50051**); the client uses the `CapabilityServiceClient` generated by `flare-grpc-proto`. Main RPCs: `ListCapabilities`, `ListUserCapabilities`, `Dispatch`, `GrantUserCapability`, `RevokeUserCapability`, `SetTenantCapabilitySwitch`. The `payload_json` of `Dispatch` is a JSON string, for example `rtc.call.video`:

```json
{ "codec": "VP8" }
```

When the process is configured with **`database_url`**, the authorization / tenant switches of `CapabilityService` go through **`PostgresCapabilityPolicy`**, sharing a connection pool with the hook configuration; both the hook and capability tables live in the "Hook engine + Capability policy" section of **`deploy/init.sql`** (`hook_configs`, `hook_executions`, `capability_user_grants`, `capability_tenant_switches`, `capability_service_settings`, `capability_audit_log`, etc.; that section performs **`DROP TABLE IF EXISTS ... CASCADE` followed by `CREATE TABLE`** for all the aforementioned objects). If you get the error `relation "capability_service_settings" does not exist`, it means the table does not exist in the **PostgreSQL instance that flare-capability is currently connected to**: a common cause is that **the script ran against a different instance/database** (for example, the orchestrator uses `5432`, while the standalone process **`flare-capability`, when `DATABASE_URL` is not set, defaults to connecting to `localhost:25432/flare2`**, see `cmd/main.rs`). At startup a `flare_capability::db` log is printed (the redacted `host:port/dbname`); please align it with the target where `deploy/init.sql` is executed. **Note**: that section drops and recreates the Hook/Capability-related tables; for a production database, evaluate the data using a migration process. When no database is configured, **`InMemoryCapabilityGrants`** is used and development sample grants are injected.

**`user capability grant missing or expired`**: `Dispatch` could not find a non-expired row in `capability_user_grants` matching **tenant_id + user_id + capability_id** (including `namespace.*`). The orchestrator defaults to **tenant_id = `0`** (see `ctx.tenant_id().unwrap_or("0")`). `deploy/init.sql` inserts **`('0','*','rtc.*')`**: `user_id = *` means any user under that tenant can use RTC (development-friendly; in production, populate per user and remove the wildcard row). If the database was created by an older version of the script, run manually:

`INSERT INTO public.capability_user_grants (tenant_id, user_id, capability_id, plan_code, source) VALUES ('0', '*', 'rtc.*', 'dev', 'manual') ON CONFLICT DO NOTHING;`

## Hook configuration sources

In this service, hook configuration supports three sources, ordered from highest to lowest priority:

### 1. Dynamic API configuration (highest priority)

**Storage location**: PostgreSQL database

**Characteristics**:
- Supports multi-tenant isolation
- Supports dynamic create/read/update/delete
- Supports version management
- Supports audit logging (records creator, creation time, update time)

**Table structure**: refer to **`deploy/init.sql`** as the source of truth (which includes columns such as `group_name`, `require_success`, `metadata`, and `created_by` aligned with `PostgresHookConfigRepository`). The following is a conceptual illustration:

```sql
CREATE TABLE hook_configs (
    id BIGSERIAL PRIMARY KEY,
    tenant_id TEXT,                    -- Tenant ID (optional, for multi-tenant isolation)
    hook_type TEXT NOT NULL,            -- Hook type (pre_send, post_send, etc.)
    name TEXT NOT NULL,                 -- Hook name
    version TEXT,                       -- Hook version
    description TEXT,                   -- Hook description
    enabled BOOLEAN NOT NULL DEFAULT true,
    priority INTEGER NOT NULL DEFAULT 100,
    group_name TEXT,                    -- Hook group (validation/critical/business)
    timeout_ms BIGINT NOT NULL DEFAULT 1000,
    max_retries INTEGER NOT NULL DEFAULT 0,
    error_policy TEXT NOT NULL DEFAULT 'fail_fast',
    require_success BOOLEAN NOT NULL DEFAULT true,
    selector_config JSONB NOT NULL DEFAULT '{}',  -- Selector configuration
    transport_config JSONB NOT NULL,               -- Transport configuration
    metadata JSONB,                                -- Metadata
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by TEXT,                               -- Creator
    
    UNIQUE(tenant_id, hook_type, name)  -- Unique constraint
);
```

**Usage** (start the full process, including the gRPC and optional plugin surface):
```rust
use anyhow::Result;
use flare_capability::domain::model::ExecutionMode;
use flare_capability::composition::{ApplicationBootstrap, CapabilityServiceConfig};

#[tokio::main]
async fn main() -> Result<()> {
    let config = CapabilityServiceConfig {
        database_url: Some("postgresql://user:pass@localhost:5432/flare".to_string()),
        tenant_id: Some("tenant-a".to_string()),
        config_file: Some("config/hooks.toml".into()),
        config_center_endpoint: Some("etcd://localhost:2379".to_string()),
        execution_mode: ExecutionMode::Sequential,
        ..Default::default()
    };
    ApplicationBootstrap::run(config).await
}
```

**Configuration management API** (via PostgresHookConfigRepository):
```rust
// Save hook configuration
repository.save(
    Some("tenant-a"),
    "pre_send",
    &hook_config_item,
    Some("admin")
).await?;

// Delete hook configuration
repository.delete(
    Some("tenant-a"),
    "pre_send",
    "hook-name"
).await?;
```

### 2. Configuration center (medium priority)

**Storage location**: etcd or Consul

**Characteristics**:
- Supports multi-tenant isolation
- Supports configuration-change watching (watch)
- Suitable for distributed environments

**Configuration key format**:
- Multi-tenant: `/flare/hooks/{tenant_id}/config`
- Global: `/flare/hooks/config`

**Usage**:
```rust
use flare_capability::domain::model::ExecutionMode;
use flare_capability::composition::CapabilityServiceConfig;

let config = CapabilityServiceConfig {
    config_center_endpoint: Some("etcd://localhost:2379".to_string()),
    tenant_id: Some("tenant-a".to_string()),
    execution_mode: ExecutionMode::Sequential,
    ..Default::default()
};
```

**Configuration format** (JSON):
```json
{
  "pre_send": [
    {
      "name": "friendship-check",
      "priority": 5,
      "timeout_ms": 50,
      "enabled": true,
      "require_success": true,
      "selector": {
        "tenants": ["tenant-a"],
        "conversation_types": ["single"]
      },
      "transport": {
        "type": "grpc",
        "endpoint": "https://hooks.relation.svc:7443"
      }
    }
  ]
}
```

### 3. Configuration file (lowest priority)

**Storage location**: local TOML file

**Characteristics**:
- Suitable for development environments
- Suitable for static configuration
- Does not support dynamic updates (requires restarting the service)

**Configuration file path**: `config/hooks.toml`

**Configuration example**:
```toml
[[pre_send]]
name = "friendship-check"
priority = 5
timeout_ms = 50
enabled = true
require_success = true

[pre_send.selector]
tenants = ["tenant-a"]
conversation_types = ["single"]
message_types = ["text", "image"]

[pre_send.transport]
type = "grpc"
endpoint = "https://hooks.relation.svc:7443"

[pre_send.retry]
max_retries = 3
retry_interval_ms = 100
backoff_strategy = "exponential"
```

## Configuration priority and merge rules

1. **Priority order**: database configuration > configuration-center configuration > configuration-file configuration
2. **Merge rule**: for hooks with the same name, the higher-priority configuration overrides the lower-priority one
3. **Load order**: loaded from lowest to highest priority, so the last-loaded configuration overrides earlier same-name configurations

## Multi-tenant support

Hook configuration supports multi-tenant scenarios:

- **Tenant isolation**: each tenant can have its own independent hook configuration
- **Global configuration**: a configuration with `tenant_id` = `NULL` applies to all tenants
- **Tenant configuration**: a specific tenant's configuration overrides the global configuration

**Query logic**:
```sql
-- When querying a tenant's configuration, both of the following are returned:
-- 1. Global configuration (tenant_id IS NULL)
-- 2. Tenant-specific configuration (tenant_id = 'tenant-a')
SELECT * FROM hook_configs
WHERE enabled = true
  AND (tenant_id IS NULL OR tenant_id = 'tenant-a')
ORDER BY hook_type, priority ASC
```

## Configuration refresh

Hook configuration hot-refresh is supported:

- **Refresh interval**: 60 seconds by default (configurable via `refresh_interval_secs`)
- **Auto-refresh**: periodically reloads configuration from all configuration sources
- **Configuration validation**: on refresh, the configuration format is validated, and invalid configurations are ignored

## Usage examples

### Basic usage

```rust
use anyhow::Result;
use flare_capability::domain::model::ExecutionMode;
use flare_capability::composition::{ApplicationBootstrap, CapabilityServiceConfig};

#[tokio::main]
async fn main() -> Result<()> {
    let config = CapabilityServiceConfig {
        config_file: Some("config/hooks.toml".into()),
        database_url: Some(
            std::env::var("DATABASE_URL")
                .unwrap_or_else(|_| "postgresql://flare:flare123@localhost:25432/flare2".to_string()),
        ),
        config_center_endpoint: Some("etcd://localhost:22379".to_string()),
        tenant_id: Some("tenant-a".to_string()),
        execution_mode: ExecutionMode::Sequential,
        refresh_interval_secs: 60,
        ..Default::default()
    };
    ApplicationBootstrap::run(config).await
}
```

To execute hooks such as PreSend within a business process, use `flare_im_hooks::HookDispatcher` (in the same process as the orchestrator); this binary is mainly responsible for the hook-extension gRPC and the capability-plugin runtime.

### Database configuration management

```rust
use flare_capability::infrastructure::persistence::PostgresHookConfigRepository;
use flare_capability::domain::models::{HookConfigItem, HookSelectorConfig, HookTransportConfig};

// Create a configuration repository
let repository = PostgresHookConfigRepository::new(
    "postgresql://user:pass@localhost:5432/flare"
).await?;


// Create a hook configuration
let hook_config = HookConfigItem {
    name: "friendship-check".to_string(),
    priority: 5,
    timeout_ms: 50,
    enabled: true,
    require_success: true,
    selector: HookSelectorConfig {
        tenants: vec!["tenant-a".to_string()],
        conversation_types: vec!["single".to_string()],
        ..Default::default()
    },
    transport: HookTransportConfig::Grpc {
        endpoint: "https://hooks.relation.svc:7443".to_string(),
        metadata: HashMap::new(),
    },
    ..Default::default()
};

// Save the configuration
let id = repository.save(
    Some("tenant-a"),
    "pre_send",
    &hook_config,
    Some("admin")
).await?;
```

## Architecture design

This service adopts a DDD + CQRS architecture:

```
flare-capability/
├── domain/              # Domain layer
│   ├── models.rs        # Hook configuration models, execution plans
│   ├── repositories.rs  # Repository interfaces
│   └── service.rs       # Domain services (orchestration service)
├── application/         # Application layer
│   ├── commands.rs      # Hook execution commands
│   ├── queries.rs       # Hook query service
│   └── service.rs       # Application service facade
├── infrastructure/      # Infrastructure layer
│   ├── adapters/        # Hook adapters (gRPC, WebHook, Local)
│   ├── config/          # Configuration loaders (file, database, configuration center)
│   ├── monitoring/      # Monitoring and statistics
│   └── persistence/     # Configuration persistence (PostgreSQL)
├── interface/           # Interface layer
│   └── grpc/            # gRPC service interface
└── service/             # Service layer
    ├── bootstrap.rs     # Application launcher
    └── registry.rs      # Service registration
```

## Configuration item reference

### Hook configuration item (HookConfigItem)

| Field | Type | Description | Default |
|------|------|------|--------|
| `name` | String | Hook name (required) | - |
| `priority` | i32 | Priority (0-1000; the smaller, the higher) | 100 |
| `timeout_ms` | u64 | Timeout (milliseconds) | 1000 |
| `enabled` | bool | Whether enabled | true |
| `require_success` | bool | Whether success is required | true |
| `error_policy` | String | Error policy (fail_fast/retry/ignore) | fail_fast |
| `max_retries` | u32 | Maximum number of retries | 0 |
| `selector` | HookSelectorConfig | Selector configuration | - |
| `transport` | HookTransportConfig | Transport configuration | - |

### Hook selector (HookSelectorConfig)

Used to match hook execution conditions:

| Field | Type | Description |
|------|------|------|
| `tenants` | Vec<String> | Tenant list (empty means match all tenants) |
| `conversation_types` | Vec<String> | Conversation-type list (empty means match all types) |
| `message_types` | Vec<String> | Message-type list (empty means match all types) |
| `user_ids` | Vec<String> | User-ID list (empty means match all users) |
| `tags` | HashMap<String, String> | Tag matching |

### Hook transport configuration (HookTransportConfig)

Supports three transport methods:

1. **gRPC transport**:
   ```toml
   [transport]
   type = "grpc"
   endpoint = "https://hooks.example.com:7443"
   ```

2. **WebHook transport**:
   ```toml
   [transport]
   type = "webhook"
   endpoint = "https://hooks.example.com/webhook"
   secret = "your-secret-key"
   ```

3. **Local Plugin transport**:
   ```toml
   [transport]
   type = "local"
   target = "plugin-name"
   ```

## Monitoring and statistics

This service provides the following hook-related monitoring metrics:

- `hook_execution_total`: total number of hook executions
- `hook_execution_duration_seconds`: hook execution duration
- `hook_success_rate`: hook success rate
- `hook_failure_total`: number of hook failures
- `hook_timeout_total`: number of hook timeouts
